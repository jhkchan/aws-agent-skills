# Example usage: securityhub-finding-troubleshooter

A walkthrough showing the skill diagnosing a CIS.1.3 NOT_AVAILABLE
finding that a generic assistant would dismiss as "wait for eval,"
demonstrating the standard-driven probe order, the
StatusReason-driven root cause (Config rule Lambda IAM gap), the
service-CLI corroboration chain, and the evidence-backed
ROOT_CAUSE_FOUND verdict.

## Input (user prompt)

> Our SOC dashboard shows a MEDIUM-severity CIS.1.3 finding in
> NOT_AVAILABLE state for 26 hours. The IAM team says all our access
> keys are rotated regularly — they don't think there's a real
> compliance gap. We've been waiting for Security Hub to "catch up"
> for over a day. What's actually wrong?

```text
Finding: arn:aws:securityhub:us-east-1:111111111111:finding/def456ghi
Standard: CIS AWS Foundations Benchmark v1.4.0
Control: CIS.1.3 (access keys ≤ 90 days old)
Severity: MEDIUM
Compliance.Status: NOT_AVAILABLE
Workflow.Status: NEW
UpdatedAt: 26 hours ago

aws securityhub get-findings:
  Compliance.StatusReasons:
    - ReasonCode: CONFIG_EVALUATION_ERROR
      Description: "Config rule Lambda invocation failed; see
        CloudWatch Logs for arn:aws:lambda:us-east-1:111111111111:function:securityhub-cis-1-3"

aws configservice describe-config-rules:
  ConfigRuleName: securityhub-cis-1-3
  Source: CustomPolicy
  LastEvaluationTime: 26 hours ago (stale)

aws logs filter-log-events (Lambda log group, last invocation):
  ERROR: AccessDenied
  Message: "User: arn:aws:sts::111111111111:assumed-role/securityhub-config-rule-role/securityhub-cis-1-3
    is not authorized to perform: iam:GetCredentialReport"

aws iam get-credential-report (latest, generated by operator):
  All active access keys rotated within the last 60 days
```

## Skill output

```text
FINDING: arn:aws:securityhub:us-east-1:111111111111:finding/def456ghi (CIS.1.3 access-key age)
VERDICT: ROOT_CAUSE_FOUND
REASON: The CIS.1.3 finding is NOT_AVAILABLE because the Config rule
  Lambda errored on a missing iam:GetCredentialReport permission. The
  keys themselves are compliant; the failure is in the evaluation layer
  (Step 8).
LAYER: AWS_SIDE
SEVERITY: MEDIUM
STANDARD: CIS
EVIDENCE:
  - Security Hub finding: Compliance.Status = NOT_AVAILABLE,
    Compliance.StatusReasons[0].ReasonCode = CONFIG_EVALUATION_ERROR.
  - Probe: describe-config-rules on securityhub-cis-1-3 shows
    LastEvaluationTime 26 hours ago.
  - Probe: filter-log-events on the rule's log group shows
    "AccessDenied: iam:GetCredentialReport" on the last invocation.
  - FP ruled out: get-credential-report shows all active keys rotated
    within 60 days — the resource state is compliant; only the
    evaluation is broken.
SUPPRESSION: Not applicable — fix the rule Lambda IAM policy.
REMEDIATION:
  1. Attach iam:GetCredentialReport to the rule's IAM role:
     aws iam put-role-policy --role-name securityhub-config-rule-role
       --policy-document file://iam-getcredential-allow.json
  2. Trigger re-evaluation:
     aws configservice start-config-rules-evaluation
       --config-rule-names securityhub-cis-1-3
  3. Verify: get-findings on CIS.1.3 returns Compliance.Status=PASSED
     within 5-15 minutes.
CONFIRM: "CONFIRM: About to attach iam:GetCredentialReport and trigger
  re-evaluation. Proceed? (yes/no)"
```

## What the skill caught that a generic assistant misses

1. **NOT_AVAILABLE is a Config rule error, not a slow eval.** A
   generic assistant sees "NOT_AVAILABLE" and tells the operator to
   "wait for the next eval cycle." The skill recognises that
   `CONFIG_EVALUATION_ERROR` is permanent — the Lambda errored, no
   amount of waiting helps. The fix is to repair the rule.

2. **The CloudWatch Logs probe isolates the missing IAM permission.**
   A generic assistant suggests "check Config" without naming the
   exact log group, log stream, or the error string. The skill probes
   `filter-log-events` on the Lambda log group and surfaces the exact
   `AccessDenied: iam:GetCredentialReport` message — the operator
   knows the precise permission to attach.

3. **The false-positive class is tested explicitly.** The skill does
   not assume "the IAM team is wrong" or "the IAM team is right." It
   pulls `get-credential-report` and verifies the resource state: if
   the keys ARE compliant, the rule Lambda is the only broken thing;
   if the keys are NOT compliant, both the rule AND the resource need
   attention. Either way, the verdict is evidence-backed.

4. **The remediation triggers immediate re-evaluation.** A generic
   assistant's "fix the IAM policy" stops short of forcing Security
   Hub to re-evaluate. The skill includes
   `start-config-rules-evaluation`, which collapses the verify window
   from "wait up to 24h for the next periodic run" to 5-15 min.

## Slash-command invocation

```
/aws:troubleshoot-securityhub-finding
```

Or via the orchestrator:

```
/aws:pipeline
You: "diagnose the MEDIUM-severity CIS.1.3 finding stuck in NOT_AVAILABLE"
```

The orchestrator emits
`[Phase: Troubleshoot | Skills routed: securityhub-finding-troubleshooter]`
and hands off to this skill for the diagnostic block.

## Live-account follow-up (optional, requires AWS CLI)

After re-evaluation, confirm the finding clears:

```bash
# Confirm the Config rule now evaluates successfully
aws configservice describe-config-rules \
  --config-rule-names securityhub-cis-1-3 \
  --profile default --output json | \
  jq '.ConfigRules[0].ConfigRuleState'
# Expect: "ACTIVE"

# Confirm Security Hub flipped the finding to PASSED
aws securityhub get-findings \
  --filters '{"GeneratorId":[{"Value":"CIS.1.3","Comparison":"PREFIX"}]}' \
  --profile default --output json | \
  jq '.Findings[0].Compliance.Status'
# Expect: "PASSED" within 5-15 minutes of the re-evaluation
```

Then watch the CIS.1.3 finding for the next 24 hours to confirm it
stays PASSED across subsequent periodic evaluations (not just the
forced re-evaluation).
