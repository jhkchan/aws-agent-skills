## Activation code registration model

### Why activation code, not IAM access keys

EKS Hybrid Nodes use an activation-based registration model. The
activation code is generated by the EKS API and tied to a specific IAM
role. The nodeadm connector agent uses this code to bootstrap kubelet,
which then obtains a client certificate for ongoing authentication.

```text
Registration flow:
  1. AWS side: create hybrid node IAM role + create access entry (HYBRID_LINUX)
  2. AWS side: generate activation code/ID
  3. On-prem: nodeadm init --activation-id <id> --activation-code <code>
  4. On-prem: nodeadm up → kubelet starts, connects to control plane
  5. Control plane: validates activation, issues client certificate
  6. Node appears in kubectl get nodes (Ready)

IAM access keys are NEVER used in this flow.
```

### Activation code properties

- **TTL:** activation codes expire (default 7 days). Re-generate if
  expired.
- **Scope:** per-cluster, tied to one IAM role.
- **Usage:** single-use per node or multi-use per group (configurable).
- **Storage:** pass to nodeadm via CLI flags or config file; do NOT
  commit to version control.

### Re-generating an expired activation code

```bash
# Check if access entry still exists
aws eks describe-access-entry \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::123456789012:role/EKSHybridNodeRole

# If the activation has expired, delete and recreate
aws eks delete-access-entry \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::123456789012:role/EKSHybridNodeRole

aws eks create-access-entry \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::123456789012:role/EKSHybridNodeRole \
  --type HYBRID_LINUX
```

Then re-run `nodeadm init` with the new activation on the affected node.

## Network path requirements

### Direct Connect (recommended)

Direct Connect provides a dedicated, private network path from the
on-prem data center to the AWS VPC hosting the EKS cluster.

```bash
# Verify Direct Connect connection
aws directconnect describe-connections \
  --query 'connections[*].{Name:connectionName,ID:connectionId,State:connectionState,Bandwidth:bandwidth}' \
  --output table

# Verify virtual interfaces
aws directconnect describe-virtual-interfaces \
  --query 'virtualInterfaces[*].{Name:virtualInterfaceName,Type:type,State:virtualInterfaceState,VLAN:vlan}' \
  --output table
```

For hybrid nodes, use a **private VIF** to route traffic to the VPC.
The EKS API endpoint must be accessible via the private VIF (private
endpoint access enabled on the cluster).

### Site-to-Site VPN (alternative)

```bash
# Verify VPN connections
aws ec2 describe-vpn-connections \
  --query 'VpnConnections[*].{ID:VpnConnectionId,State:State,CustomerGW:CustomerGatewayId}' \
  --output table
```

VPN tunnels provide an encrypted IPsec path to the VPC. Latency is
typically higher than Direct Connect (internet-based).

### Latency and heartbeat requirements

Kubelet sends heartbeats to the control plane every 10 seconds
(default). If the control plane does not receive a heartbeat within the
`node-monitor-grace-period` (default 40s), the node is marked NotReady.

| Latency | Impact |
|---|---|
| < 50ms | Excellent — Direct Connect private VIF |
| 50-100ms | Good — acceptable for most workloads |
| 100-250ms | Marginal — may cause intermittent NotReady under load |
| > 250ms | Problematic — VPN over long distances; risk of NotReady |
| > 1000ms | Not viable — nodes will be marked NotReady |

### Testing connectivity from on-prem

```bash
# On the on-prem node:
# Test EKS API reachability
curl -k https://<eks-endpoint>/healthz
# Expected: ok (HTTP 200)

# Test latency
ping -c 10 <eks-endpoint-host>
# Check average latency and packet loss

# Test ECR reachability
curl -I https://<account-id>.dkr.ecr.us-east-1.amazonaws.com/
# Expected: HTTP 403 (auth required, but endpoint reachable)
```

## Security group mapping (on-prem firewall rules)

### Why hybrid nodes do NOT use VPC security groups

Hybrid nodes are on-prem servers, not EC2 instances. They are NOT in
the VPC and cannot have VPC security groups attached. Network security
is enforced by on-prem firewall rules (iptables, firewalld, hardware
firewall, etc.).

### Required firewall rules

| Traffic | Source | Destination | Port | Protocol | Purpose |
|---|---|---|---|---|---|
| EKS API | On-prem node | EKS API endpoint | 443 | TCP | kubelet → control plane |
| ECR | On-prem node | ECR endpoints | 443 | TCP | Container image pulls |
| SSM | On-prem node | SSM endpoints | 443 | TCP | Session Manager |
| CloudWatch | On-prem node | CW endpoints | 443 | TCP | Metrics + logs |
| STS | On-prem node | STS endpoints | 443 | TCP | IAM credential exchange |
| Inter-node | On-prem node | On-prem node | 10250 | TCP | kubelet API |
| Inter-node | On-prem node | On-prem node | varies | TCP | CNI pod networking |

### On-prem firewall configuration (iptables example)

```bash
# Allow EKS API (replace with actual endpoint IP)
iptables -A OUTPUT -p tcp -d <eks-api-ip> --dport 443 -j ACCEPT

# Allow ECR
iptables -A OUTPUT -p tcp -d <ecr-ip> --dport 443 -j ACCEPT

# Allow inter-node communication (kubelet)
iptables -A INPUT -p tcp --dport 10250 -s 10.0.0.0/16 -j ACCEPT
iptables -A OUTPUT -p tcp --dport 10250 -d 10.0.0.0/16 -j ACCEPT
```

## nodeadm connector agent

### Installation

```bash
# On the on-prem node (Amazon Linux, Ubuntu, or RedHat):
curl -O https://s3.us-east-1.amazonaws.com/amazon-eks/hybrid-node-tools/nodeadm
chmod +x nodeadm
mv nodeadm /usr/local/bin/
```

### Bootstrap flow

```bash
# Step 1: Initialize with activation credentials
nodeadm init \
  --cluster-name my-cluster \
  --cluster-endpoint https://XXXX.gr7.us-east-1.eks.amazonaws.com \
  --cluster-ca <base64-encoded-ca> \
  --activation-id <activation-id> \
  --activation-code <activation-code> \
  --node-role arn:aws:iam::123456789012:role/EKSHybridNodeRole

# Step 2: Start kubelet
nodeadm up

# Step 3: Verify
kubectl get nodes --show-labels | grep $(hostname)
```

### nodeadm configuration file

nodeadm can also read from a YAML config:

```yaml
# /etc/nodeadm/config.yaml
cluster:
  name: my-cluster
  endpoint: https://XXXX.gr7.us-east-1.eks.amazonaws.com
  certificateAuthority: <base64-ca>
activation:
  id: <activation-id>
  code: <activation-code>
node:
  roleArn: arn:aws:iam::123456789012:role/EKSHybridNodeRole
  labels:
    node-group: hybrid
    topology: on-prem
```

Then run `nodeadm up --config /etc/nodeadm/config.yaml`.

### Troubleshooting nodeadm

| Symptom | Cause | Fix |
|---|---|---|
| Node not appearing | Network path blocked | Test `curl -k https://<endpoint>/healthz` |
| Node NotReady | High latency or kubelet crash | Check `systemctl status kubelet` |
| Activation failed | Expired code or wrong IAM role | Re-generate activation, verify role ARN |
| Container runtime error | containerd not running | `systemctl start containerd` |
| Image pull errors | ECR network path blocked | Open 443 to ECR endpoints |

## Upgrade flow

```bash
# 1. Upgrade control plane first
aws eks update-cluster-version --name my-cluster --kubernetes-version 1.31

# 2. Upgrade nodeadm on each node (rolling, one at a time)
kubectl cordon on-prem-node-01
kubectl drain on-prem-node-01 --ignore-daemonsets --delete-emptydir-data

# On the node:
nodeadm upgrade --version 1.31

kubectl uncordon on-prem-node-01
kubectl get node on-prem-node-01   # Wait for Ready

# 3. Repeat for each node
```

Always upgrade the control plane first. Node kubelet versions can lag
by one minor version (k8s skew policy), but do not upgrade nodes before
the control plane.

## Expert heuristic: network path is non-negotiable (moved from SKILL.md)

A baseline model says "nodes just need internet." The correct heuristic
recognizes that nodes MUST reach the EKS control plane API.

```text
On-prem Node (10.0.1.5)
  │
  ├── Must reach: EKS API endpoint (TCP 443)
  │
  ├── Network path options:
  │     ├── Direct Connect (private VIF → VPC)     ← RECOMMENDED
  │     ├── Site-to-Site VPN (IPsec → VPC)          ← Acceptable
  │     └── Public internet (EKS public endpoint)   ← NOT recommended
  │
  └── Latency requirement:
        ├── kubelet heartbeat: every 10s (default)
        └── If latency > grace period (40s) → node → NotReady
```

**Key implication:** verify the network path BEFORE registering nodes.
A node that registers then loses connectivity will be marked NotReady
within 40 seconds (default kubelet grace period).


## nodeadm registration CLI (Step 3) (moved from SKILL.md)

```bash
# On the on-prem node (NOT an AWS CLI command):
# Download and install nodeadm
curl -O https://s3.us-east-1.amazonaws.com/amazon-eks/hybrid-node-tools/nodeadm
chmod +x nodeadm

# Configure and start
./nodeadm init \
  --cluster-name my-cluster \
  --cluster-endpoint https://XXXX.gr7.us-east-1.eks.amazonaws.com \
  --cluster-ca <base64-ca> \
  --activation-id <activation-id> \
  --activation-code <activation-code> \
  --node-role arn:aws:iam::123456789012:role/EKSHybridNodeRole

./nodeadm up

# Verify registration (from a machine with kubectl)
kubectl get nodes --show-labels | grep hybrid
# Expected: node appears with Ready status
```
