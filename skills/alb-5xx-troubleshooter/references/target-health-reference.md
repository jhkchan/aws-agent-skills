# ALB Target Health and Access Log Reference

Supplementary reference for the ALB 5xx Troubleshooter skill. This is
loaded on-demand when a diagnostic needs target health reason codes,
access log field positions, security group evaluation rules, or
health check timing relationships.

## ALB 5xx error code catalog

### 500 InternalServerError

| Attribute | Detail |
|---|---|
| Meaning | The ALB itself failed to process the request. |
| Frequency | Rare. |
| Typical cause | AWS-side incident. |
| Action | Check AWS Health Dashboard; if sustained, ESCALATE. |
| CloudWatch signal | HTTPCode_ELB_5XX_Count spikes (note: ELB-level, not Target-level). |

### 502 BadGateway

| Attribute | Detail |
|---|---|
| Meaning | Target returned an invalid HTTP response, or the connection to the target failed. |
| Frequency | Common. |
| Typical causes | Target application crash; target returning non-HTTP bytes; connection reset; target SG blocking ALB; target port closed. |
| Access log signal | `error_reason` field: `Target.InvalidResponse`, `Target.ConnectionFailed`. |
| Action | Test the target directly; check target SG; inspect target application logs. |

### 503 ServiceUnavailable

| Attribute | Detail |
|---|---|
| Meaning | No healthy target is available to receive the request. |
| Frequency | Common during deployments or after health check failures. |
| Typical causes | All targets unhealthy (health check failing); all targets draining; zero registered targets; target group not attached to listener. |
| Access log signal | No `target_status_code` (no target was selected); `target_group_arn` present but `target:port` field is `-`. |
| Action | Check `describe-target-health`; verify health check config; register new targets. |

### 504 GatewayTimeout

| Attribute | Detail |
|---|---|
| Meaning | Target did not respond within the ALB idle timeout (default 60s). |
| Frequency | Common for slow applications. |
| Typical causes | Target application slow; idle timeout too short for the workload; target stuck (deadlock, resource exhaustion). |
| Access log signal | `error_reason: Target.Timeout`; `target_processing_time` approaches the idle timeout value. |
| Action | Raise idle timeout or optimize target; consider async pattern. |

### 561 Unauthorized

| Attribute | Detail |
|---|---|
| Meaning | WAF blocked the request (custom error response). |
| Frequency | Depends on WAF configuration. |
| Typical causes | WAF rule false positive; rate-based rule triggered; IP-based block. |
| Access log signal | `error_reason` may reference WAF; `elb_status_code: 561`. |
| Action | Review WAF Web ACL rules and logs; add exemptions for false positives. |

## ELB 5xx vs Target 5xx

A common source of confusion: the ALB returns a 5xx that ORIGINATED at
the target (the target returned 500/502/503) vs a 5xx that ORIGINATED at
the ALB itself (no healthy target, connection failed).

| Metric | What it measures | Meaning |
|---|---|---|
| `HTTPCode_ELB_5XX_Count` | 5xx generated BY the ALB | ALB-level failure: 502 (connection failed), 503 (no healthy targets), 504 (timeout), 561 (WAF). |
| `HTTPCode_Target_5XX_Count` | 5xx returned BY the target | Target-level failure: the target application returned 500/502/503. The ALB passes this through to the client. |

**Key distinction:** If `HTTPCode_Target_5XX_Count` spikes but
`HTTPCode_ELB_5XX_Count` does NOT, the target is returning 5xx — the ALB
is healthy and passing the response through. The fix is in the target
application, not the ALB.

## Target health reason codes

### describe-target-health State values

| State | Meaning | ALB routes traffic? |
|---|---|---|
| `healthy` | Target passed health checks | YES |
| `unhealthy` | Target failed health checks | NO |
| `initial` | Target is being registered; health checks in progress | NO |
| `unused` | Target is registered but the target group is not attached to a listener | NO |
| `draining` | Target is deregistering; serving in-flight requests only | NO (new requests) |

### unhealthy Reason values

| Reason | Description | Likely cause |
|---|---|---|
| `Target.FailedHealthChecks` | Health check requests failed (non-matching status code or timeout) | Health check path/port/matcher wrong; application unhealthy |
| `Target.Timeout` | Health check request timed out | `HealthCheckTimeoutSeconds` too short; target too slow to respond |
| `Target.NotRegistered` | Target is not registered to the target group | (Rare — usually a transient state) |
| `Target.NotInUse` | Target group is not attached to any listener | Listener misconfiguration; attach the TG |
| `Elb.InternalError` | ALB internal error during health check | AWS-side issue; ESCALATE |
| `Target.InvalidResponse` | Target returned an invalid response to the health check | Target returning non-HTTP or malformed HTTP on the health check path |

## Health check timing relationships

### The critical timing formula

```
time_to_detect_failure = HealthCheckIntervalSeconds * UnhealthyThresholdCount
```

Example: interval 30s, unhealthy threshold 3 → a failed target is marked
`unhealthy` after 90 seconds. During those 90 seconds, the ALB continues
routing traffic to the failing target.

### The critical recovery formula

```
time_to_recover = HealthCheckIntervalSeconds * HealthyThresholdCount
```

Example: interval 30s, healthy threshold 3 → a recovered target is marked
`healthy` after 90 seconds. During those 90 seconds, the ALB does NOT
route traffic to the recovering target.

### Deregistration delay vs health check timing

If `HealthCheckIntervalSeconds * UnhealthyThresholdCount` exceeds the
deregistration delay, a failing target may be deregistered (after
draining) BEFORE the health check marks it `unhealthy`. The ALB sends
traffic to a dying target throughout the gap. Always verify the timing
relationship when tuning dereg delay.

## ALB access log format (key fields)

The ALB access log is space-delimited. Field positions (1-indexed):

| Position | Field | What it tells you |
|---|---|---|
| 1 | `time` | Request timestamp |
| 2 | `elb` | ALB ARN |
| 3 | `client:port` | Client IP and port |
| 4 | `target:port` | Target IP and port (or `-` if no target selected) |
| 9 | `target_processing_time` | Time spent at the target (seconds) |
| 11 | `elb_status_code` | Status returned to client (the 5xx) |
| 12 | `target_status_code` | Status from the target (`-` if no target selected) |
| 14 | `received_bytes` | Request body size |
| 15 | `sent_bytes` | Response body size |
| 18 | `user_agent` | Client User-Agent |
| 21 | `target_group_arn` | Target group for this request |
| 22 | `trace_id` | X-Amzn-Trace-Id |
| Last | `error_reason` | The failure reason (502/503/504 specific) |

### error_reason values

| `error_reason` | Meaning | Layer |
|---|---|---|
| `Target.InvalidResponse` | Target returned malformed HTTP | TARGET_INVALID_RESPONSE |
| `Target.ConnectionFailed` | Connection to target failed (refused, reset, SSL) | TARGET_SG_BLOCKED / TARGET_INVALID_RESPONSE |
| `Target.Timeout` | Target did not respond within idle timeout | TARGET_TIMEOUT |
| `Target.HealthCheckFailed` | Target failed health checks (not directly a 5xx cause) | TARGET_HEALTH_CHECK |

## Security group evaluation for ALB-to-target traffic

### The correct pattern

```
Client → ALB SG (inbound on 80/443) → ALB → Target SG (inbound on target port from ALB SG)
```

| Component | Rule | Source |
|---|---|---|
| ALB SG inbound | Allow tcp/80 and tcp/443 from client CIDRs (0.0.0.0/0 for internet-facing) | Client IPs |
| ALB SG outbound | Allow tcp/<target-port> to target SG (or all) | Target SG |
| Target SG inbound | Allow tcp/<target-port> from ALB SG (referenced by SG ID) | ALB SG ID |
| Target SG outbound | Allow ephemeral (1024-65535) to ALB SG (or all) | ALB SG ID |

### Common SG misconfigurations

| Misconfiguration | Symptom | Fix |
|---|---|---|
| Target SG allows ALB IP, not ALB SG | 502 when ALB scales (new IP) | Replace IP with ALB SG reference |
| Target SG allows 0.0.0.0/0 on target port | Direct access bypassing ALB | Restrict to ALB SG |
| Target SG allows port 80 but target group uses 443 | 502 (connection refused on 443) | Add rule for 443 |
| Health check port different from target port, SG only allows target port | Targets `healthy` (health check on allowed port) but 502 on actual traffic | Add rule for BOTH ports or align the ports |

### IP-type targets in peered VPCs

IP-type targets in a peered VPC or on-premises CANNOT use referenced SG
rules. The target SG must use CIDR-based rules:

```
Target SG inbound: Allow tcp/<target-port> from <ALB-subnet-CIDR>
```

This is because the ALB SG reference only works within the same VPC. A
referenced-SG rule for a cross-VPC IP target is silently ignored.

## Listener rule evaluation

### Priority order

Listener rules are evaluated in ascending priority order. The lowest
numeric priority that matches the request conditions is applied.

| Priority | Condition | Action |
|---|---|---|
| 1 | `path-pattern: /api/*` | forward to tg-api |
| 2 | `path-pattern: /static/*` | forward to tg-static |
| 10 | `path-pattern: /*` (catch-all) | forward to tg-default |
| default | (no rule matches) | DefaultActions: forward to tg-default |

### Common rule misconfigurations

| Misconfiguration | Symptom |
|---|---|
| Low-priority catch-all (`/*`) shadows specific rules | All traffic goes to the catch-all target group |
| Host-header condition does not match incoming Host | Request falls through to default action |
| Default action points to deleted/empty target group | 503 for any request not matching a specific rule |
| Rule conditions reference wrong target group ARN | 503 (target group has no healthy targets) |

## CloudWatch metrics for ALB 5xx diagnosis

### Namespace: AWS/ApplicationELB

| Metric | What it tells you |
|---|---|
| `HTTPCode_ELB_5XX_Count` | 5xx generated BY the ALB (502, 503, 504, 561). |
| `HTTPCode_Target_5XX_Count` | 5xx returned BY the target application (target app error). |
| `TargetResponseTime` | Time from request sent to target until response received. Approaching idle timeout indicates 504 risk. |
| `HealthyHostCount` | Number of healthy targets. Dropping to zero → 503. |
| `UnHealthyHostCount` | Number of unhealthy targets. Spiking → health check failures. |
| `RejectedConnectionCount` | Connections rejected by the ALB (capacity issues). |
| `TargetConnectionErrorCount` | Connection errors to targets (SG or port issues). |

### Key dimensions

| Dimension | Use |
|---|---|
| `LoadBalancer` | Per-ALB metrics. The value is the ARN suffix (`app/prod-web/abc123`). |
| `TargetGroup` | Per-target-group metrics. Combined with LoadBalancer for per-TG-per-ALB granularity. |
| `AvailabilityZone` | Per-AZ metrics. Identifies AZ-specific issues. |

### NLB namespace: AWS/NetworkELB

NLB metrics are similar but use different names:
- `HealthyHostCount`, `UnHealthyHostCount` (same).
- `TCP_Target_Reset_Count` — target sent a TCP RST.
- `ConsumedLCUs` — NLB capacity units.
- No HTTP-level metrics (NLB is L4).

## Idle timeout reference

| Setting | Default | Max | Notes |
|---|---|---|---|
| ALB idle timeout | 60s | 4000s | Applies to both frontend (client-ALB) and backend (ALB-target) connections. |
| NLB idle timeout | 350s | 4000s | TCP-level; applies to the connection, not individual requests. |
| Target group deregistration delay | 300s | 3600s | Time targets stay in `draining` state after deregistration. |

### When to raise the idle timeout

| Workload | Recommended idle timeout | Rationale |
|---|---|---|
| Standard web API | 60s (default) | Most API calls complete in < 5s. |
| File upload (large) | 120-300s | Large uploads on slow connections take > 60s. |
| Long-polling | 120-300s | Client holds connection for updates. |
| Report generation | Migrate to async | Do not raise timeout for > 300s workloads. |
| WebSocket | Use WebSocket support | ALB supports native WebSocket upgrade. |

## WAF on ALB

### 561 error code

WAF blocks produce a 561 error code from the ALB (custom response). The
request never reaches the target.

### WAF log analysis

```bash
# WAF logs in CloudWatch Logs
aws logs filter-log-events \
  --log-group-name aws-waf-logs-<acl-name> \
  --filter-pattern '"action":"BLOCK"' \
  --start-time $(date -u -d '-1 hour' +%s)000 \
  --output json | jq '.events[].message'
```

WAF log fields:
- `action`: `BLOCK`, `ALLOW`, `COUNT`, `CAPTCHA`.
- `ruleId`: The rule that matched.
- `requestHeaders`: Full request headers (for false-positive analysis).
- `rateBasedRuleList`: Rate-based rules that triggered.

### Common WAF false positives

| Rule | False positive trigger |
|---|---|
| SQL injection rule | Legitimate SQL-like strings in query parameters (e.g., `SELECT` in a search box) |
| XSS rule | Legitimate HTML/script content in API payloads |
| Size restriction | Legitimate large file uploads |
| Rate-based rule | Legitimate high-traffic clients (CDN, monitoring) |
